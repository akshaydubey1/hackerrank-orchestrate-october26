## 3b. Bounded investigation step (agent capability)

**Problems.** (1) A screenshot's declared record count exceeds the row ids extracted (dataset: evidence_37 declares 6 records; the default OCR pass drops `audit_record_002`, and the verifier's identical pass drops it too). (2) Screenshot OCR sometimes misreads an identifier (dataset: evidence_32 reads `areed1433@gmail.com` as `areedi433` / `areedt433`). The previous code accepted a one-edit look-alike as exposure (fuzzy). That rule is removed. Instead, when an OCR token is a near-miss of exactly one known identifier, a policy chooses which deterministic re-extraction to run (re-OCR at ×2/×3 with different page segmentation, optional binarisation) under a budget of 3 per problem and 60 per run. An identifier is accepted **only** if a re-extraction reads it verbatim as a whole token; recovered rows **only** if the total then equals the screen's declared count, and they are parsed by the ordinary document parser from their own line. Policies cannot read other files, accept or edit facts, or touch temporal filtering, policy rules or serialisation (unit tests U4–U7, mutant 'accept investigation hypothesis without verbatim read').

## 7. Independent verifier

`code/evaluation/verifier.py` imports none of the predictor's decision code. It rebuilds identifier sets from the CSVs, re-extracts the cited file itself (own pdftotext / Tesseract calls), locates the record context by plain text search, and checks: the citation was captured by audit_at and its line is not dated after it; every planned resource is discoverable by audit_at; the cited context supports the claimed state; the context names no other subject; every finding has remediation and verification; recreation paths are closed before records are treated; retained records are verified and never deleted without a cited expired retention date; COMPLETE contains only cited, supported verification; absence is not proven from a partial capture; canonical order and numbering; active flows/restores visible in admissible evidence are planned.

### 9.1 What "uncertified" means in the output

COMPLETE requires every required final state to be proven by a cited admissible observation **before** the status
is chosen, including the subject's primary account. An account is proven only when it is identified (an identifier
in admissible evidence, or the unique workflow submission for this request alone) and its state is observed. A
missing account id is not proof of absence, and a set of absent candidates is not proof about the subject unless
evidence shows the set is exhaustive and contains the subject's account (a report-time window shows neither).
Cases with no supported violation but an unproven required state are UNCERTIFIED and serialised as INCOMPLETE with
only the future verification checks (empty evidence_id, no invented findings). If the organisers expect COMPLETE for
these, they score as status errors; if they expect the account to be attributed by request order, the gold answers
depend on information this design deliberately excludes.

## 11. Remaining limitations (honest list)

* **71 unique uncertified cases** in the 518-case output (Section 9.1): not proven incomplete, not proven
  complete. Reason assignments can exceed the case count (see Metric definitions).
* **Account attribution** is the dominant blocker; the only admissible way to identify an account is an identifier in
  admissible evidence or the unique workflow submission for the request alone.
* **Late-captured files are ignored entirely** (C1); if the key uses them, the affected steps are missed by design.
* **Absence proofs** come only from explicit 404 / NOT_FOUND observations, single-capture JSON collections covering
  the subject and full-table replica dumps; SQL inventories never prove absence.
* **Restore capability** needs a statement about the specific archive.
